# Diagnóstico do projeto — CortadorLive (gerador-cortes) · 2026-09-16

**Objetivo declarado:** publicar uma nova release no GitHub, com a aplicação **agnóstica** (outra pessoa instala, cria o próprio canal e faz seus cortes) e com uma **reorganização estrutural inspirada no projeto `investimentos` (BolsoFundo)** — Clean Architecture + DDD tático leve, contrato tipado, regras de negócio rastreáveis.

**Método:** fan-out de 16 subagentes read-only (skill `project-diagnostic`). 13 lentes invocaram uma skill explicitamente; 3 lentes pedidas pelo dono não têm skill (agnosticismo, performance backend, gate de qualidade). Nenhum arquivo do projeto foi alterado; a única escrita é este relatório.

---

## Resumo executivo

O CortadorLive é um produto **funcional, bem testado e com domínio rico** — backend com 3.277 testes verdes, ruff limpo, ~70 módulos de domínio puro, frontend sem `any`/`console.log`/mojibake, composições Remotion determinísticas. O que ele **não é, ainda, é publicável nem portátil**, e sua **estrutura não acompanhou o crescimento**.

Três forças puxam na mesma direção:

1. **A release está bloqueada por coisas concretas e baratas.** A `main` local está **481 commits à frente do GitHub**: nada desde a v0.2.0 (06/07) passou por CI, gitleaks, audit ou lock-check. O lint do frontend e do renderer está **vermelho** (1 erro cada). O `CHANGELOG` parou no D-431, o README descreve o app de julho e o SETUP manda um passo que **impede o boot** de quem o seguir. Há demandas fechadas sem validação e pendências de PROD em aberto.

2. **O app ainda só funciona "na máquina do Paulo".** O render final codifica **só em `h264_qsv`** (sem GPU Intel, quebra). Toda a IA de texto depende de **assinatura pessoal** (`claude -p`/`agy`), sem opção por API key. Só sobe via **PowerShell**. Não há checagem de pré-requisitos nem guia de OAuth do YouTube. Há **dado pessoal de terceiro** (nome + e-mail) versionado no renderer, persona editorial "analítica/política" nos defaults, e porta `8000` fixa em ~12 lugares (DEV lê/escreve em PROD).

3. **A arquitetura existe no papel, mas as setas apontam para o lado errado nos pontos críticos.** `models.py` importa um service; `infrastructure/` importa `services/`; há ciclos de import mascarados por **208 imports tardios**; 15 módulos soltos na raiz de `app/`; routers com SQL e regra de negócio; *god-services* (`claude_ia.py` 1.771 linhas). No frontend, **três cascas de UI** coexistem (legado/Workbench/upgrade), o contrato HTTP é **escrito à mão em 13 cópias** de `request()`, e o tipo `CenaRemotion` existe em **três versões** ligadas por cast. Os ciclos de vida `StatusCorte`/`StatusProjeto` **não têm dono** — são mutados livremente em routers e services. Nada disso é verificado por máquina (sem import-linter, sem lint de fronteiras).

**Recomendação de sequência** (detalhada em "Próximos passos"): **v0.3.0 = release consolidada e agnóstica** (bloqueadores + portabilidade mínima + docs + guarda-corpos arquiteturais em modo "aviso"); **v0.4.0+ = migração estrutural por contexto**, guiada pela estrutura-alvo abaixo e por ADRs. Tentar reorganizar a arquitetura *antes* de publicar misturaria 481 commits não verificados com uma refatoração ampla — o pior cenário para bisect e rollback.

## Estrutura-alvo inspirada no `investimentos`

As lentes de arquitetura extraíram do BolsoFundo **regras**, não a sintaxe .NET. Resumo (detalhe completo nas seções `clean-architecture-guardian (backend)`, `(frontend + renderer)` e `domain-driven-design`):

**Regras que atravessam:**
1. **Dependência para dentro por contexto**: `<contexto>/{domain, application, infrastructure, api}`. `domain` não importa sqlalchemy/fastapi/httpx/subprocess/PIL/`os.environ`. Só `bootstrap.py` conhece adaptadores concretos.
2. **Regra de negócio mora no domínio e é testada**; routers só traduzem HTTP ↔ caso de uso.
3. **Casos de uso explícitos** (uma função/classe por caso de uso), **sem CQRS/mediator/event sourcing**.
4. **Portas via `typing.Protocol`** (`GeradorIA`, `CanalAtivo`, `UnidadeDeTrabalho`, `ExecutorProcesso`, `PublicadorYoutube`).
5. **Contrato OpenAPI versionado + cliente TS gerado** — o frontend nunca escreve tipo de DTO à mão.
6. **Erros de domínio → problem+json** num handler global.
7. **Rastreabilidade RN-xx/D-xxx** em docstrings, summaries de rota e testes; catálogo em `docs/dominio/`.
8. **Fronteiras verificadas por máquina** (import-linter no backend, `eslint-plugin-boundaries` no front).
9. Frontend **feature-first**: `app/` (casca única) · `shared/` (api gerada, ui, lib) · `entities/` (corte, cena) · `features/<x>/{api,model,ui,pages,index.ts}`.

**Contextos propostos (backend):** `core` · `canal` · `ia` · `editorial` · `descoberta` · `ingestao` · `analise` · `corte` · `render` · `metadados` · `shorts` · `publicacao` (+ retenção dentro de publicação). Árvore, regras de import e tabela de/para com locks: ver seção `clean-architecture-guardian (backend)`.

**Catálogo inicial RN-01…RN-25** (ciclos de Projeto/Corte, duração líquida, cascata parcial de layout, herança do gancho, regra do Limpar, teto de hashtags, thumbnail 4:4:4 etc.): ver seção `domain-driven-design`.

#### Regras extraídas do investimentos (traduzidas p/ Python)
1. **Quatro camadas com dependência para dentro:** `domain ← application ← infrastructure / api`. O domain não importa sqlalchemy, fastapi, httpx, subprocess, os.environ, PIL nem `app.infrastructure`. Em Python, cada "projeto" .NET vira um subpacote por contexto (`<contexto>/domain`, `application`, `infrastructure`, `api`). A pasta `Core/` do .NET não tem equivalente útil em Python: o próprio pacote já é o namespace. Guarda-se a intenção (a raiz do pacote só tem o ponto de entrada), com `main.py`/`bootstrap.py` na raiz e todo o resto dentro de contextos.
2. **A regra de negócio mora no domain e é testada:** cálculos e decisões (status de corte, elegibilidade de publicação, duração líquida, ranking) são funções ou value objects de domínio. Nunca em router nem em SQL do router.
3. **A borda só traduz** (ADR-0003 §2): o router monta o comando/consulta, chama o caso de uso e projeta o DTO de saída. Nada de repositório, `db.execute`, `create_task` ou montagem de legenda no router.
4. **Casos de uso explícitos, sem barramento ou CQRS** (ADR-0003 §3): uma função ou classe por caso de uso em `application/`, registrada de forma simples (Depends/factory). Nada de mediator.
5. **Portas definidas por dentro** (`Application/Core/Abstractions`: IClock, ICurrentOwnerProvider, IUnitOfWork): em Python, `typing.Protocol` em `application/ports.py` (Relogio, UnidadeDeTrabalho, GeradorIA, ExecutorProcesso, PublicadorYoutube, CanalAtivo), implementadas na infrastructure.
6. **Um ponto único de composição** (a Api como composition root, cada camada com `AddX()`): em Python, `bootstrap.py` com `montar_dependencias()`, e cada contexto expõe `registrar(app)` e/ou providers para `Depends`. Só esse ponto conhece concretos de infrastructure.
7. **Contrato OpenAPI tipado e versionado** (ADR-0002/0003 §4): todas as rotas com `response_model`, enums como string, `backend/openapi.json` gerado e versionado, teste no CI que falha se houver diff, frontend consumindo só o cliente gerado (`openapi-typescript`).
8. **Erros padronizados** (D-012, ProblemDetails): `ErroDeDominio(categoria)` → handler global → `application/problem+json` (400/404/422), e 500 genérico sem internals.
9. **Contexto do dono/canal como seam** (`ICurrentOwnerProvider`): uma porta `CanalAtivo` resolve "de quem são os dados". Não fica espalhada via `channel_paths` em cerca de 45 módulos.
10. **Testes por camada, espelhando `src`:** `tests/<contexto>/domain` (puro, sem I/O), `application` (casos de uso com fakes das portas), `infrastructure` (integração real com sqlite/ffmpeg, marcador `integration`), `api` (TestClient + contrato OpenAPI) e um `tests/architecture` com import-linter.

#### Regras extraídas do investimentos (frontend)
1. **Contrato único gerado**: `npm run gen:api` → `services/api/schema.d.ts` a partir de `backend/openapi.json` versionado; clientes **nunca** importam código do backend (AGENTS.md, D-010; ADR-0002).
2. **Porta única para os tipos brutos**: `services/api/contract.ts` só reexporta `components["schemas"][...]`; nada importa `schema.d.ts` direto → regeneração toca um ponto só.
3. **Um único client HTTP**: `services/api/client.ts` com `openapi-fetch` tipado por `paths`, base resolvida num lugar (proxy do Vite em dev, same-origin em teste para MSW), `apiUrl()` para links de download.
4. **Fetchers + mappers DTO→UI**: `services/<dominio>.ts` chama `apiClient.GET(...)` → `unwrap` → `mapX` devolve tipo de UI (`services/types.ts`); features nunca veem DTO cru nem `apiClient`.
5. **Erros padronizados**: `problem-details.ts` converte a resposta de erro em `ApiProblemError` que chega via `mutation.error`.
6. **Feature-first**: `features/<x>/` com `api/` (um hook TanStack Query por arquivo, ex. `get-net-worth.ts`), `components/` (burros, com teste ao lado) e `lib/` (regras puras).
7. **Páginas finas + casca única**: `pages/*Page.tsx` compõe features; `app/` concentra layout, `navigation.ts` (fonte única de rotas/menu), `query-client.ts`, settings.
8. **Nunca fetch no componente**: toda leitura via hook em `features/<x>/api/` + `AsyncBoundary` de 4 estados (vazio/carregando/erro/sucesso).
9. **`components/` compartilhado é só design system** (DataTable, Drawer, states, form, icons) — sem importar features.
10. **Import entre features é baixo e pontual** (≤5 de `portfolio`), sempre para um hook/componente exportado, nunca para o interior de outra feature.
